# Phase 00 — 범위·가설·품질 목표 확정

**선행 조건:** GitLab 프로젝트 접근 및 CI Runner 확인. **산출물:** 실행 가능한 수용 테스트 명세, 권리 범위, 벤치마크 픽스처 및 아키텍처 가설.

## 해야 할 일

1. 사용 사례 세 가지를 분리한다.
   - A: 단일 Infohash로 1080p 테스트 MP4 연속 재생.
   - B: **서로 다른 Infohash에 동일한 바이트 파일** 포함, 두 소스의 다운로드 기여 관측.
   - C: 서로 다른 1080p 인코딩(H.264, HEVC 등)을 구간별 변환/전환.
2. 테스트 미디어는 재배포 가능한 합성 영상으로 제작한다. 2~5분 baseline, 오프닝 +350ms, fps 23.976/24/30, 오디오 +120ms offset, HDR→SDR 변종, 편집 컷 차이 버전을 준비한다.
3. 네트워크 시나리오: 정상, 토렌트 A의 급격한 속도 하락, B의 특정 구간 부재, tracker timeout, DHT-only, NAT 도달 실패, 전체 오프라인, 1Mbps 제약 등을 재현한다. 제어 가능한 peer/seeder 환경 사용.
4. 제품 SLO를 **목표치**로 정의하고 실측 결과를 분리 기록한다. 시작 지연 p50/p95, stall 횟수/분 및 총 stall ratio, goodput, buffer underrun, A/V sync drift, CPU/GPU/메모리/디스크, 전력, 배터리.
5. 기록한 사용자 소스만 받아들이는 기본 모델을 선택한다. 인덱싱/검색·DRM 우회·불법 유통 카탈로그 구축은 범위 밖.
6. 피어 수의 세 정의: discovered / connected / delivering_verified_bytes. 1차 최적화 지표는 세 번째.
7. 최소 제품: 재생 중 하나의 영상만으로도 정상 동작할 것; multi-swarm은 최적화 계층일 것.

## 초기 수용 목표(실험값으로 조정)

- 합성 1080p 로컬/제어된 WAN 실험에서 재생 성공률 99% 이상을 **목표**로 두고 첫 baseline 측정 후 수치 승인.
- 잘못된 장면 정렬로 인한 무음/검은 화면/순서 오류는 0건.
- 실패한 보조 스웜이 정상 단일 스웜 재생을 악화시키지 않을 것.
- source가 없거나 권리가 불확실하면 UI는 재생 가능하다고 주장하지 않을 것.
- 비용·RAM·스토리지의 상한을 CLI 또는 API에서 변경할 수 있을 것.

## 산출물·검증 게이트

- docs/TEST_MATRIX.md의 픽스처 생성 명령 및 기댓값 확정.
- 별도의 scope/benchmark 이슈와 각 시나리오의 결과 기록 템플릿 생성.
- 성공: 사용 사례 A/B/C가 상호 구분되고 각각 실패/성공 관찰 방법이 존재.
- 실패 시: 작품 동등성, 인코딩 정렬 정확도, 용량 목표의 가정을 먼저 축소.

## 범위 외

콘텐츠 불법 수집, 계정/DRM 보호 우회, 무단 트래커 접근, 다운로드 숨김/우회 기능, 클라우드 다중 사용자 SaaS, 실시간 4K HDR 무조건 지원 약속.
